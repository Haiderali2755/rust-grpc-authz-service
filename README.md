# Ultra-Low-Latency gRPC Authz Service (Rust)

A gRPC microservice for distributed session validation and rate limiting, built
with Tonic and backed by Redis. Includes a load generator that reports the full
latency distribution, plus Docker and Kubernetes manifests.

**Personal project** — built to measure what a Rust gRPC service on Redis
actually delivers, not to demonstrate a predetermined number.

## What it does

One `Check` RPC does two things in a single call:

1. **Resolves a session token** to a principal (Redis `GET`)
2. **Consumes one unit of that principal's rate budget** (Redis Lua script)

It returns `ALLOW`, `DENY_UNAUTHENTICATED`, or `DENY_RATE_LIMITED`, along with
remaining quota and the window reset time.

### The rate limiter is atomic, deliberately

The limit check runs as a [Lua script](src/limiter.lua) inside Redis rather than
as `GET` → decide → `SET` from the service. With separate commands, N concurrent
requests can each read the same counter, each conclude they are under the limit,
and collectively blow past it. Redis executes scripts atomically, so the
increment and the decision cannot interleave.

This is the kind of bug that only appears under concurrency, which is exactly
when a rate limiter matters.

### Redis failure is not silently "allow"

If Redis is unreachable the RPC returns `UNAVAILABLE` rather than defaulting to
allow or deny. A caller must be able to distinguish "you are denied" from "the
authorizer is down" — conflating them either opens a security hole or causes an
outage, depending on which way you default.

## Measured results

Load generated by [a Rust client](bench/loadgen) recording every request into an
HdrHistogram, so the percentiles below are real quantiles. Single host, service
capped at 2 CPU / 512 MiB, Redis on loopback.

| Concurrency | Throughput | p50 | p99 | Requests < 1ms |
|---:|---:|---:|---:|---:|
| 1 | 3,852 rps | **0.240 ms** | 0.505 ms | 99.9% |
| 2 | 6,767 rps | **0.276 ms** | 0.573 ms | 99.9% |
| 4 | 10,526 rps | **0.357 ms** | 0.729 ms | 99.8% |
| 8 | 14,628 rps | **0.517 ms** | 1.095 ms | 98.5% |
| 16 | 17,823 rps | 0.847 ms | 1.767 ms | 72.9% |
| 32 | 19,313 rps | 1.591 ms | 3.019 ms | 3.4% |
| 64 | 23,123 rps | 2.713 ms | 4.387 ms | 0.0% |

570,764 requests at concurrency 64 with **zero errors**.

### Reading these numbers honestly

**Sub-millisecond is real, but it is a property of load level, not of the
service alone.** Up to ~14,600 req/s the p50 stays under 0.52 ms and 98.5% of
all requests complete inside 1 ms. Past that the service saturates and queueing
dominates.

**Why the curve bends.** This is a closed-loop benchmark, so Little's Law
applies: `latency ≈ concurrency / throughput`. At 64 in-flight requests and
23,123 rps, 64 / 23,123 ≈ 2.8 ms — which is what p50 measures. Beyond the knee
at ~32 concurrency, extra load buys almost no throughput and costs latency
proportionally. **A single "sub-millisecond" figure with no stated concurrency
is not a meaningful claim**, which is why the table reports the whole curve.

**What is being measured.** End-to-end gRPC round trip including the Redis
round trip, client and server on the same machine. A real deployment adds
network hops between client, service, and Redis — expect higher absolute
numbers and a lower knee.

## Deployment

Kubernetes manifests in [`k8s/`](k8s/) — chosen for latency-sensitive serving:

- **Guaranteed QoS** (requests == limits). Burstable pods get CPU-throttled
  mid-request, which lands directly in tail latency.
- **Headless Service.** gRPC holds long-lived HTTP/2 connections, so a normal
  ClusterIP pins each client to one pod. Clients resolve all pod IPs and
  balance per request.
- **gRPC-native probes** rather than an exec probe — the image ships no shell.
- **HPA scales up fast, down slow.** Shedding replicas eagerly causes
  connection churn and a tail-latency bump on every scale-down.
- **PodDisruptionBudget** keeps 2 of 3 replicas during node drains.
- Non-root, read-only root filesystem, all capabilities dropped.

The `Secret` in [k8s/hpa.yaml](k8s/hpa.yaml) is a local-testing placeholder.
Real clusters should source it from a secret manager, not a committed manifest.

## Running it

Requires Docker. Nothing else — the toolchain runs in containers.

```bash
./bench/run_benchmark.sh
```

Tunable:

```bash
CONCURRENCY=8 DURATION=60 ./bench/run_benchmark.sh
```

Output lands in `bench/results/`. Raw sweep data: [`bench/results/sweep.json`](bench/results/sweep.json).
