Reading this curve

Sub-millisecond is real, but it is a property of load level — not of the service alone. Median latency stays under 1 ms up to about 17,823 req/s. Past that the service saturates and queueing dominates.

Why it bends. This is a closed-loop benchmark, so Little's Law applies: latency ≈ concurrency ÷ throughput. At 64 in-flight requests and 23,123 rps, 64 ÷ 23,123 ≈ 2.8 ms — which is what p50 measures there. Beyond the knee near 32 concurrency, extra load buys almost no throughput and costs latency proportionally.

So a bare "sub-millisecond" claim means little. Without a stated concurrency and percentile it is unfalsifiable, which is why the whole curve is published rather than one flattering point.

Running on Kubernetes

Deployed to a kind cluster from the manifests in k8s/ — 3/3 replicas Ready, zero restarts. Driving the same client through the cluster: 26,136 RPCs, 0 errors, 1.47 ms p50 at concurrency 4.

Higher than the 0.36 ms measured over plain Docker at the same concurrency. The difference is kubectl port-forward — a userspace TCP proxy — plus pod networking, not the service. Quoting the Docker figure for a Kubernetes deployment would be wrong, so both are recorded.

What is being measured

End-to-end gRPC round trip including the Redis round trip, client and server on one host. Every latency is recorded into an HdrHistogram, so the percentiles are real quantiles rather than an average with error bars.

A real deployment adds network hops between client, service, and Redis — expect higher absolute numbers and a lower knee. Redis runs with persistence disabled; this measures the service, not Redis durability.
